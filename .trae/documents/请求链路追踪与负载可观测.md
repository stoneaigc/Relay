# 请求链路追踪：让「一次请求如何路由、如何故障转移、负载如何分配」可观测

## Summary（目标）

针对你的两个质疑补齐可观测性：
1. **日志请求链路**：为每次请求生成 `request_id`，把「用户 → 请求模型 → resolve_all 候选顺序 → 每个候选的尝试(成功/熔断跳过/Unavailable/failover) → 最终结果」完整记录下来。
2. **负载策略可视化**：一次请求进来后 "A/B/C/D 怎么转移"——把候选顺序(加权随机命中 + failover 次序)、每个候选的权重、实际选中、切换轨迹全部内嵌到链路里展示，而不是只给聚合数字。

**你的上游治理能不能看？** 现有 [UpstreamsPanel](file:///h:/AI%20创造营/AI%20编程/runapi/frontend/admin/src/App.tsx) + `/admin/api/upstreams` 已能看每个上游的**熔断状态、并发槽占用**（见 [list_upstream_status](file:///h:/AI%20创造营/AI%20编程/runapi/src/state.rs#L466)）。缺的是**单次请求的 failover 转移轨迹**——这正是本次要补的，与现有面板互补、不重复。

## Current State（现状，Phase 1 探索结论）

- 数据面 [handlers.rs](file:///h:/AI%20创造营/AI%20编程/runapi/src/handlers.rs) `run_chat`(L64-199)/`run_messages`(L385-503) 无任何 tracing 日志，单请求不可追踪。
- 无 `request_id`：`usage_logs`/`FailureRecord`/metrics 互不关联。
- `resolve_all`([routing.rs:L67](file:///h:/AI%20创造营/AI%20编程/runapi/src/routing.rs#L67)) 的 `Resolved` 不含 weight；`out` 数组顺序=加权命中+failover 次序，`Target.weight` 在 shuffle 前可拿。
- `usage_logs` 只写成功计费(status 硬编码 200)，失败请求不入库；`FailureRecord` 内存 500 条只记最后失败候选、不落库。
- 成熟异步落库：`UsageEvent` + mpsc([main.rs:L81](file:///h:/AI%20创造营/AI%20编程/runapi/src/main.rs#L81)) + `background_task`([main.rs:L202](file:///h:/AI%20创造营/AI%20编程/runapi/src/main.rs#L202)) 逐条 insert_usage。
- 前端扩展点：NAV 数组(L47) + Routes(L103-121) + api.ts api 对象(L58-140) + UI 原语。

## 设计决策

1. **新建 `request_logs` 表**存全量请求链路（成功+失败）；`usage_logs` 保持账单语义仅加 `request_id` 列关联。两表并存，不污染账单统计。
2. **存储抽象 `RequestLogStore` trait**：默认 `SqliteRequestLogStore`（写 request_logs，零新依赖）；预留 `ElasticsearchRequestLogStore` 占位（暂不接，因无 ES 环境）。config `[logging].store=sqlite|elasticsearch` 切换，默认 sqlite。
3. **`Resolved` 加 `weight` 字段**，使候选链能记录权重。
4. **异步写库**复用 mpsc 模式，热路径不阻塞。

## 与现有系统协同（不重复造轮子）

| 观测维度 | 现有能力 | 本次新增/补齐 |
|---|---|---|
| 上游熔断/并发状态 | `/admin/api/upstreams` + UpstreamsPanel ✅ | 无需新增 |
| 失败审计(最后失败候选) | `record_failure` + FailureRecord + 失败面板 ✅ | 保留，request_logs 是全量超集 |
| 请求量/成功率/延迟/tokens 聚合 | metrics + MetricsPanel ✅ | 不变 |
| **单次请求的候选顺序+权重+实际选中** | ❌ 无 | 新增：request_logs.candidates |
| **单次请求的 failover 转移轨迹** | ❌ 无 | 新增：request_logs.attempts |
| **失败请求可追溯(哪些请求失败/为何/切到哪)** | ❌ 不入库 | 新增：request_logs 全量落库 |

## Proposed Changes（改动清单）

### 后端
1. **migrations/0001_init.sql + postgres**：新增 `request_logs` 表；`usage_logs` 加 `request_id TEXT` 列。表字段：id/request_id/user_id/path/requested_model/stream/candidates(TEXT JSON)/attempts(TEXT JSON)/final_kind/final_upstream_model/final_status/latency_ms/input_tokens/output_tokens/charged_tokens/created_at；索引(user_id, created_at)、(request_id)。SQLite 用 `ALTER TABLE usage_logs ADD COLUMN request_id`(对已存在库幂等)。
2. **src/config.rs**：`[logging]` 段 `store: String`(默认 sqlite)。
3. **src/routing.rs**：`Resolved` 加 `pub weight: i64`，`resolve_all` 透传 `t.weight`。
4. **新文件 src/reqlog.rs**：`RequestLog`/`RequestAttempt` 结构 + `trait RequestLogStore` + `SqliteRequestLogStore` + `ElasticsearchRequestLogStore`(占位)。
5. **src/state.rs**：AppState 加 `request_log: Arc<dyn RequestLogStore>`、`request_log_tx: mpsc::Sender<RequestLog>`；`UsageEvent` 加 `request_id`。
6. **src/handlers.rs**：`run_chat`/`run_messages` 生成 request_id；每个候选尝试收集 attempts(状态/延迟/错误/是否熔断跳过)；结束构造 RequestLog(成功失败都发)；`UsageEvent` 带 request_id。
7. **src/main.rs**：构造 store(按 config)、接线 channel 与消费 task、UsageEvent 带 request_id。

### 查询端点
8. **src/admin.rs**：`GET /admin/api/request-logs?q=&limit=&from=`(倒序分页，SQLite LIKE 检索 request_id/用户名/model)。

### 前端
9. **api.ts**：`RequestLogRow` 类型 + `requestLogs({q,limit})`。
10. **App.tsx**：NAV 加 "/request-log 请求链路"；新增 `RequestLogPanel`：搜索框(request_id/用户/模型) + 列表(时间/用户/模型/path/候选数/最终状态) + 行展开显示 candidates 权重表与 attempts failover 链，失败/熔断行变色(复用 Card/Table/Badge)。

## Assumptions & Decisions
- 记录全部请求(成功+失败)到 request_logs；usage_logs 仍只成功计费(加 request_id 关联)。
- 负载策略内嵌链路；不做独立面板。
- 暂不接 ES：仅 trait 占位 + 配置开关，SQLite 默认可用；后续补 ES 实现不改业务代码。
- 异步 mpsc 消费，channel 4096(与 usage_tx 一致)。
