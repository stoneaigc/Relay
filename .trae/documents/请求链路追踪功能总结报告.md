## 1. 功能概述

本次为 RunAPI 新增**请求链路追踪（Request Trace）**能力，核心目标是回答两个运维/可观测问题：

1. **一次请求到底怎么路由的？** —— 用户请求的对外模型名，经 `resolve_all` 解析后产生一组候选上游，其**加权命中顺序 + failover 次序 + 权重**全部记录；实际选中哪个、是否发生切换、切换轨迹如何，全部落库可查。
2. **上游故障时怎么转移的？** —— 当某个上游不可用（连接失败 / 429 / 5xx）时，请求如何 failover 到下一个候选；当某上游连续失败触发熔断时，候选被跳过；这些**转移轨迹**逐条记录。

该能力**与既有观测面板互补而非重复**：`UpstreamsPanel` 看上游级熔断/并发状态、`MetricsPanel` 看聚合指标；本次补的是**单次请求的 failover 转移轨迹**这一此前完全缺失的维度。

---

## 2. 设计目标与决策

| 维度 | 设计决策 | 理由 |
|---|---|---|
| 记录范围 | 成功 + 失败**全量**落库 | 失败请求此前完全不入库，无法追溯 |
| 存储隔离 | 新建 `request_logs` 表；`usage_logs` 仅加 `request_id` 列关联 | 账单语义与链路追踪语义分离，不污染账单统计 |
| 存储抽象 | `RequestLogStore` trait + `SqliteRequestLogStore`（默认）+ `EsRequestLogStore`（占位） | 默认零新依赖；后续接 ES 不改业务代码 |
| 权重记录 | `Resolved` 新增 `weight` 字段 | 候选链可内嵌负载策略，而非只给聚合数字 |
| 落库方式 | mpsc channel + `background_task` 异步消费 | 热路径不阻塞，与既有 `UsageEvent` 落库一致 |
| 可重试错误 | 新增 `ApiError::Unavailable`（传输/429/5xx）区分 `Upstream`（4xx 非重试） | failover 只在可重试时切换，语义正确 |
| 配置开关 | `[logging].store = sqlite \| elasticsearch` | 运行时切换存储后端 |

## 3. 数据模型

### 3.1 链路日志结构（`src/reqlog.rs`）

```rust
/// 单个候选上游的一次尝试结果（failover 链的一环）。
pub struct RequestAttempt {
    pub kind: String,          // openai / anthropic
    pub base_url: String,
    pub upstream_model: String,
    pub weight: u32,           // 该候选在路由中的权重
    pub status: i32,           // 200=成功; 503=不可用; -1=熔断跳过; 4xx/500=其它错误; 0=候选列表初始态
    pub latency_ms: u32,
    pub error: String,
}

/// 一次完整请求的链路日志（成功 + 失败均记录）。
pub struct RequestLog {
    pub request_id: String,        // UUID v4
    pub user_id: String,
    pub path: String,             // chat | messages
    pub requested_model: String,
    pub stream: bool,
    pub candidates: Vec<RequestAttempt>,  // resolve_all 候选顺序（加权命中 + failover 次序）
    pub attempts: Vec<RequestAttempt>,    // 每个候选的实际尝试结果
    pub final_kind: Option<String>,
    pub final_upstream_model: Option<String>,
    pub final_status: i32,        // 200=成功; 非200=失败
    pub latency_ms: u32,
    pub input_tokens: u32,
    pub output_tokens: u32,
    pub charged_tokens: i64,
    pub ts: i64,                  // unix 秒
}
```

- `RequestLog`/`RequestAttempt` 均实现 `Serialize + Deserialize`（用于 SQLite JSON 列存取与单测往返）。
- `RequestLogStore` trait 使用 `Pin<Box<dyn Future>>` 实现 dyn-compatible async，可被 `Arc<dyn RequestLogStore>` 持有。

### 3.2 存储后端（`src/reqlog.rs`）

| 实现 | 说明 |
|---|---|
| `SqliteRequestLogStore` | 默认。`write` 序列化 `candidates`/`attempts` 为 JSON 写入 `request_logs`；`recent` 支持 `q` 检索（`request_id`/`model` LIKE）+ `limit`（clamp 1~200），倒序分页 |
| `EsRequestLogStore` | 占位实现，`write`/`recent` 均 `bail!("elasticsearch ... is not implemented yet; use sqlite")`，保留 trait 契约 |

### 3.3 数据库 schema（`migrations/0001_init.sql`）

```sql
-- 请求链路追踪表：记录每次请求(成功+失败)的路由候选顺序、权重、实际选中、failover 链。
CREATE TABLE IF NOT EXISTS request_logs (
  id                 INTEGER PRIMARY KEY AUTOINCREMENT,
  request_id         TEXT NOT NULL,
  user_id            TEXT NOT NULL,
  path               TEXT,
  requested_model    TEXT,
  stream             INTEGER NOT NULL DEFAULT 0,
  candidates         TEXT,        -- JSON
  attempts           TEXT,        -- JSON
  final_kind         TEXT,
  final_upstream_model TEXT,
  final_status       INTEGER,
  latency_ms         INTEGER NOT NULL DEFAULT 0,
  input_tokens       INTEGER NOT NULL DEFAULT 0,
  output_tokens      INTEGER NOT NULL DEFAULT 0,
  charged_tokens     INTEGER NOT NULL DEFAULT 0,
  created_at         TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_reqlog_user ON request_logs(user_id, created_at);
CREATE INDEX IF NOT EXISTS idx_reqlog_reqid ON request_logs(request_id);

-- usage_logs 新增关联列
ALTER TABLE usage_logs ADD COLUMN request_id TEXT;
```

> `usage_logs` 保持账单语义（仅成功计费），仅加 `request_id` 列关联到 `request_logs`，两表并存不互相污染。

## 4. 异步落库链路

```
热路径(run_chat/run_messages)
   │  构造 RunTrace { request_id, candidates, attempts, ... }
   │  emit_success / emit_error  ──► state.request_log_tx.send(log)
   ▼
mpsc::channel<RequestLog>(4096)        ◄── 容量与 usage_tx 一致
   │
   ▼
background_task (tokio::spawn)
   └─ select! {
        req_rx.recv()  ──►  state.request_log.write(&l).await   // 落 SQLite
        rx.recv()       ──►  storage::insert_usage(...)
        tick(5s)        ──►  flush_dirty(...)
      }
```

- `RunTrace::emit_success(state, input, output, charged)`：成功结算，补 tokens 后投递。
- `RunTrace::emit_error(state, final_status)`：失败结算，tokens 全为 0，投递。
- 落库失败仅 `tracing::error!` 记录，不影响请求返回（`let _ = ...send(...)` 丢弃 send 结果）。

## 5. 路由与 failover 语义

### 5.1 路由解析（`src/routing.rs`）

- `Resolved` 新增 `weight: i64`，`resolve_all` 透传 `t.weight`。
- `resolve_all` 返回的候选数组顺序 = **加权随机命中 + failover 次序**（shuffle 前权重可取）。

### 5.2 可重试错误分类（`src/error.rs` + `src/providers/*.rs`）

```rust
// error.rs：新增 Unavailable（可重试），与 Upstream（非重试 4xx）区分
ApiError::Unavailable(String)  // 连接失败 / 超时 / 5xx / 429
ApiError::Upstream(String)    // 其它上游错误（如 4xx，非重试）
```

```rust
// providers/openai.rs 与 providers/anthropic.rs：
.send().await.map_err(|e| ApiError::Unavailable(format!("transport: {e}")))?;  // 传输失败 → 可重试
if code == 429 || code >= 500 {
    return Err(ApiError::Unavailable(format!("{code}: {text}")));             // 429/5xx → 可重试
}
return Err(ApiError::Upstream(format!("{code}: {text}")));                   // 其余 4xx → 非重试
```

### 5.3 handlers 中的 failover 循环（`src/handlers.rs` `run_chat` / `run_messages`）

```rust
let candidates = state.routing.load().resolve_all(user.group(), &model)?;
let cand_init = init_candidates(&candidates);   // 候选初始列表（weight 已填，status 未定）
let mut attempts: Vec<RequestAttempt> = Vec::new();
let final_status: i32 = 200;                    // 最终状态，默认成功
for r in &candidates {
    let ukey = UpstreamKey::new(kind, base_url, api_key);

    // P2：熔断检查 —— 若该上游处于熔断窗口，跳过并记 status=-1
    if state.breaker_should_skip(&ukey).await {
        attempts.push(RequestAttempt { ..., status: -1, error: "breaker open, skip".into() });
        continue;
    }

    // P1：占用上游并发槽
    let slot = state.acquire_upstream(ukey.clone(), provider_name).await;

    match kind {
        ProviderKind::Openai => { ... }   // 成功→emit; Unavailable→continue(failover); 其它→emit_error+return
        ProviderKind::Anthropic => { ... } // 同上
    }
}
```

**三种状态语义：**

| 状态 | 含义 | 触发条件 |
|---|---|---|
| `200` | 成功命中 | 上游返回成功 |
| `503` | 不可用 | `ApiError::Unavailable`（连接/超时/429/5xx），failover 切换下一候选 |
| `-1` | 熔断跳过 | 该上游处于熔断窗口（`BREAKER_FAILS=3`、`BREAKER_WINDOW=30s`、半开），未实际调用 |
| `4xx`/`500` | 非重试错误 | 直接返回（不切换），`final_status` 记为该错误码 |

## 7. 查询接口（`src/admin.rs`）

```rust
/// GET /admin/api/request-logs?q=&limit=50 —— 最近请求链路日志（倒序）。
pub async fn list_request_logs(
    State(state), headers,
    Query(q): Query<RequestLogsQuery>,  // { q, limit }
) -> Result<Json<Value>, ApiError> {
    admin_guard(&state, &headers)?;
    let logs = state.request_log.recent(q.q.as_deref().unwrap_or(""), q.limit.unwrap_or(50)).await?;
    Ok(Json(json!({ "data": logs })))
}
```

路由注册（`main.rs`）：`.route("/request-logs", get(admin::list_request_logs))`，挂载在 `/admin/api` 前缀下。

- **行展开**：
  - **候选顺序（负载策略）**表：`#` / 上游 / 模型 / 权重 / 状态（在 attempts 中查找对应候选状态）。
  - **实际尝试（failover 链）**表：上游 / 模型 / 状态 / 延迟 / 错误。
  - **Tokens 汇总**：↑输入 ↓输出 / 计费 / stream 标记。
- **状态标签**（`attemptStatusColor` / `attemptStatusLabel`）：

| 状态 | 颜色 | 标签 |
|---|---|---|
| `200` | 绿 | `200 OK` |
| `-1` | 琥珀 | `熔断跳过` |
| `503` | 玫红 | `503 不可用` |
| `0` | 灰 | `未尝试` |
| `>=500` | 玫红 | `{status}` |
| 其余 | 灰 | `{status}` |
