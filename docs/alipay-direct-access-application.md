## 三、业务与技术形态（判断是否为「已自建经营系统」的关键）

Relay 是自托管 LLM API 网关，**商品、订单、权益三套系统已经自建并上线在跑**，因此属于官网描述的「基础收款能力」适用对象，而不是需要全托管的零代码场景：

- **商品与套餐**：后台可配置多个套餐（`plan`），每个套餐含价格、`token` 额度、周期重置规则、购买次数上限、可绑定的模型用户组。
- **订单**：已建 `payment_orders` 表落每一次支付请求，含本地单号、用户、套餐、金额快照、状态机（pending → paid / failed）。金额快照在下单时固化，下游发货一律以本地表为准，不采信回调报文中的数字。
- **幂等发货**：改单动用原子的 `UPDATE ... WHERE status='pending'`，只有抢到状态迁移的请求才发货，重复回调不会重复发放额度。
- **权益**：发放即写入 `plan_quota` 额度桶并同步内存态，同时按套餐配置切换用户的模型组访问权限；失败按「业务性失败置终态待人工」与「临时故障退回待支付等重投」两类分治。
- **渠道抽象**：后端已抽出 `PaymentProvider` 层，上层路由与发货逻辑与渠道无关，切换支付方式只改一个配置项，不改业务代码。

结论：**我方只需要一条合规的收款 + 结算能力，订单与权益不需要支付宝托管。**

## 六、为什么希望走独立接入而不是合作平台

- 已在用的合作平台模式**无沙箱环境**，联调即真实交易，且**退款/对账/交易查询接口尚未开放**，争议订单只能人工处理；
- 我方已有完整的订单与权益体系，经平台中转只是多一层接口依赖，并未带来额外的结算或风控收益（资金流向同样是直达创作者账户），却抬高了单点的故障影响面；
- 应用部署在境外机房，每多一层跳转就多一分支付拉起失败率，链路越短越稳。
- 直连后可减少一层网络跳转，对境外部署的应用来说能明显降低支付拉起耗时与丢单率。
